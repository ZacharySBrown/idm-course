### Phase 3 — Audio asset tooling

**3a. `shared/tools/extract_clips.py`** — small Python tool, ffmpeg wrapper.
- Reads `clip_manifest.yaml`'s `song_clips:` block
- For each entry: cuts `<song_source_dir>/<source>` at `start..end` with optional `fade_in_ms`/`fade_out_ms`/`normalize_lufs`
- Writes to `<build_root>/audio/clips/<episode_id>/<clip_id>.wav`
- CLI: `python shared/tools/extract_clips.py --course-root courses/ableton-devices --lesson e01-operator [--clip <id>] [--dry-run]`
- Imports `_course_lib`. Reuse the `repo_root()`, `load_course()`, `episodes_dir()` patterns from existing shared tools.
- Output dir = `<repo_root>/build/ableton-devices/audio/clips/e01-operator/`
- Dependencies: `ffmpeg` on PATH (already required for `build_episode.py`). Use `pyloudnorm` for the `normalize_lufs` step or skip and document.

**3b. `operator-render` tool** — the harder one. Lives in **this repo** (not stemforge), uses stemforge as a runtime dep.

User said: *"build the feature here for now, and assume stemforge as a dep ... I'm doing some patching to stemforge right now that I don't want to touch."*

Architecture, modeled on stemforge's BOUNCE button (see [`~/zacharysbrown/stemforge/docs/clip-export-button-wiring.md`](../../../../zacharysbrown/stemforge/docs/clip-export-button-wiring.md) for the canonical pattern):

```
courses/ableton-devices/tools/operator_render/
├── README.md
├── operator_render.py             # Python CLI driver — entry point
├── m4l/
│   ├── OperatorRender.amxd        # Max for Live device (built from operator_render.maxpat)
│   ├── operator_render.maxpat     # source patcher
│   └── operator_render.js         # JS engine: reads spec, applies LOM params, freezes track
└── lom_param_map.json             # Operator LOM param name → friendly name mapping
```

Workflow:

1. User opens an Ableton template set with one MIDI track. The track has the `OperatorRender.amxd` device at chain start, then an Operator instance.
2. User runs `python courses/ableton-devices/tools/operator_render/operator_render.py --course-root courses/ableton-devices --episode e01-operator [--demo <id>]`. The CLI:
   - Reads `clip_manifest.yaml` → `operator_demos:`
   - Writes a per-demo spec JSON to a known path (modeled on stemforge's `command.json` IPC)
   - Spawns nothing — just waits. The M4L device does the work.
3. The user clicks a button on the M4L device labeled **RENDER**. The JS:
   - Reads the spec JSON
   - For each demo: applies Operator parameters via LiveAPI `set` calls (e.g., `live_set tracks 0 devices 1 parameters Algorithm 1`), inserts the MIDI clip into slot 0 of the track, sets clip length, calls `track.freeze()`, polls `track.freezing` until 0
   - When freeze done: locates the freeze WAV in `<live_set_dir>/Samples/Processed/Freeze/`, renames to `<demo_id>.wav`, moves to `<repo_root>/build/ableton-devices/audio/clips/e01-operator/<demo_id>.wav`
   - Calls `track.unfreeze()`, clears clip slot, reports completion via NDJSON event (stemforge pattern)
4. The Python CLI watches the output dir and reports per-demo progress.

Key references for the next session:
- **Stemforge BOUNCE wiring** → [`~/zacharysbrown/stemforge/docs/clip-export-button-wiring.md`](../../../../zacharysbrown/stemforge/docs/clip-export-button-wiring.md)
- **Stemforge bridge JS pattern** → [`~/zacharysbrown/stemforge/m4l/stemforge_bridge.js`](../../../../zacharysbrown/stemforge/m4l/stemforge_bridge.js)
- **Stemforge LOM JS pattern** → [`~/zacharysbrown/stemforge/m4l/stemforge_lom.js`](../../../../zacharysbrown/stemforge/m4l/stemforge_lom.js)
- **Stemforge clip-export Python helper** → `~/zacharysbrown/stemforge/tools/m4l_export_clips.py`
- **Live LOM reference** → https://docs.cycling74.com/max8/vignettes/live_object_model
- **Operator's LOM-exposed parameter names** are not in the public docs by default — easiest path: build a small "dump-params" message that walks `live_set tracks 0 devices 1 parameters` and prints names + indices. Run it once, save the dictionary to `lom_param_map.json`. The Operator parameters we need (per the 16 patch demos in `clip_manifest.yaml`):
  - Algorithm number
  - Per-operator: On, Coarse, Fine, Level, Wave, Feedback (A only typically), Phase, R (retrigger), envelope ADSR + slope curves, envelope mode (None/Loop/Beat/Sync/Trigger)
  - Filter: Type, Frequency, Resonance, Drive, Circuit
  - Spread, Voices, Glide, Time, Tone, Volume
  - LFO: Shape, Rate, Range, Amount

**3c. `track.freeze()` quirks worth knowing:**
- Freeze is asynchronous in Live. Poll `track get freeze_state` (returns 0=not freezing, 1=freezing, 2=frozen) — actual property name varies, verify with a small probe message.
- Freeze WAVs land in `<live_set_dir>/Samples/Processed/Freeze/`. Filename is auto-generated. Identify the new file by mtime delta or by listing before/after.
- Frozen tracks include the device chain *before* the frozen point but typically **don't** include sends. Verify against a known-output reference patch.
- The whole track freezes (not just one clip) — make sure the only thing on the track is the Operator instance and the MIDI clip.
- Need to call `unfreeze` (or "Flatten" via LOM) before re-rendering to avoid stacking freezes.

### Phase 4 — Episode assembly

Extend [`shared/tools/build_episode.py`](../../shared/tools/build_episode.py) so each slide's `demos: [list]` injects the named clip WAVs **after** that slide's narration WAV in the concat order. Right now build_episode just concatenates `narr_dir / <slide.script_md.stem>.wav`.

New behavior:
```python
for slide in lesson["slides"]:
    pieces.append(narration_wav)
    for demo_id in slide.get("demos", []):
        pieces.append(<build_root>/audio/clips/<episode_id>/<demo_id>.wav)
```

The `<build_root>/audio/clips/<episode_id>/` dir is fed by both `extract_clips.py` (song clips) and `operator_render.py` (patch demos). A clip can come from either source — the IDs are unique across both lists in `clip_manifest.yaml` (song clips have human names, operator demos all start with `op-`).

After Phase 4, the full pipeline for ep01:
```bash
# 1. Extract song clips (fast, deterministic)
python shared/tools/extract_clips.py --course-root courses/ableton-devices --lesson e01-operator

# 2. Render Operator patches (manual M4L button click per session, but scriptable)
python courses/ableton-devices/tools/operator_render/operator_render.py --course-root courses/ableton-devices --episode e01-operator
# → user clicks RENDER button in Ableton → tool watches and reports

# 3. Render voiceover (~$2 OpenAI cost first run, cached after)
python shared/tools/render_voiceover.py --course-root courses/ableton-devices --lesson e01-operator

# 4. Assemble
python shared/tools/build_episode.py --course-root courses/ableton-devices --lesson e01-operator
# → build/ableton-devices/audio/episodes/e01-operator.mp3 + chapters

# 5. Audition + iterate
```

## Open questions / risks

1. **Operator LOM parameter names** — not in public Cycling docs. Plan: write a small probe `.maxpat` that dumps `live_set tracks 0 devices 1 parameters` and saves names+indices to `lom_param_map.json`. The 16 patch demos in `clip_manifest.yaml` are the test corpus.
2. **Freeze WAV cleanup** — frozen WAVs may include silence padding before the first MIDI note + after the release tail. The `operator_render` post-step should trim to `[clip_start, clip_start + duration_s + tail_buffer]` and normalize to a target LUFS so the patch demos sit consistently against narration.
3. **Stria sourcing** — user reported it's acquired (`songs/ableton-ep01/09_stria.wav`, 180MB). Verify quality before committing the cuts at `1:30–1:45` and `3:30–3:45`. If not the right pressing, fall back: replace `stria-excerpt-1` and `stria-excerpt-2` with hand-built Operator patches at 1:φ ratio (already the recommended fallback in `clip_manifest.yaml`).
4. **`French Kiss` clip start time** — manifest specifies `1:22–1:30`. Different rips of the track may have different intros. Adjust on audition.
5. **Build_episode silence padding between narration + clip** — current code inserts 400ms silence between WAVs. May be too short for clip→narration transitions; consider per-slide override or smarter crossfading. Decide on first audition.
6. **Live template set** — the operator-render tool needs a known `.als` template with the M4L device + Operator on track 0. Either commit a `template.als` to `courses/ableton-devices/episodes/e01-operator/` or document the exact track setup in README.
